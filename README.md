# Currency Rates Service

Асинхронный сервис котировок валют: клиент запрашивает обновление курса,
получает идентификатор задания и позже забирает результат — само обновление
выполняется в фоне пулом воркеров.

Стек: **Go 1.25** (стандартный `net/http`, без фреймворков), **PostgreSQL 18**
(`pgx/v5`), внешний источник курсов — [frankfurter.dev](https://frankfurter.dev)
(данные ЕЦБ, без API-ключа).

## Как это работает

```
client ──POST /rates/updates──▶ handler ──▶ service ──INSERT──▶ PostgreSQL
   ◀── 202 {id, status: pending}              │
                                              ▼  сигнал «есть работа»
                                          workers × N
                                              │ claim: SELECT ... FOR UPDATE
                                              │        SKIP LOCKED → in_progress
                                              ▼
                                   provider (frankfurter, retry)
                                              │
                        транзакция: completed + UPSERT последней котировки

recovery-поллер (каждые 30 c и на старте):
  зависшие in_progress (старше 5 мин) → pending + сигнал воркерам
```

- **Идемпотентность in-flight**: пока по паре есть незавершённое задание,
  повторный POST возвращает идентификатор существующего
  (partial unique index + `INSERT ... ON CONFLICT`). После завершения
  следующий POST создаёт новое задание.
- **Устойчивость**: retry к провайдеру с паузами; потерянные при сбое задания
  подбирают poll-тикер воркера и recovery-поллер. При остановке сервиса
  незавершённое задание возвращается в `pending` и переделывается после
  старта.

## API

| Метод | Путь | Ответ |
|---|---|---|
| POST | `/api/v1/rates/updates` | `202` — задание создано или возвращено существующее |
| GET | `/api/v1/rates/updates/{id}` | `200` — статус, цена, время; `404` — нет такого id; `400` — id не UUID |
| GET | `/api/v1/rates/latest?pair=EUR/MXN` | `200` — последнее значение; `404` — пара ещё не обновлялась |

```bash
# создать задание (регистр и пробелы вокруг кодов нормализуются)
curl -X POST localhost:8080/api/v1/rates/updates \
  -H 'Content-Type: application/json' -d '{"pair":"EUR/MXN"}'
# → {"id":"...","pair":"EUR/MXN","status":"pending","price":null,"updated_at":null}

# результат по идентификатору (через пару секунд)
curl localhost:8080/api/v1/rates/updates/<id>
# → {"status":"completed","price":21.0226,"updated_at":"..."}

# последнее значение по паре
curl 'localhost:8080/api/v1/rates/latest?pair=EUR/MXN'
```

Полная спецификация — [`api/openapi.yaml`](api/openapi.yaml).
При запуске через docker compose по адресу `http://localhost:8081` доступен
Swagger UI для просмотра спецификации.

## Запуск

### Docker (рекомендуется)

```bash
docker compose up --build -d
```

Поднимаются PostgreSQL (схема применяется автоматически init-скриптом
`migrations/001_init.sql` при первом старте с чистым volume), сервис
(`:8080`) и Swagger UI (`:8081`). Дополнительная настройка не требуется.

Сброс с удалением данных (например, после изменения схемы):

```bash
docker compose down -v && docker compose up --build -d
```

### Локально

```bash
docker compose up -d postgres   # база наружу на localhost:5433
go run ./cmd/server             # .env не обязателен: есть дефолты
```

## Конфигурация

Переменные окружения. Приоритет: окружение → `.env` (godotenv) → дефолты
в коде. Файл `.env` в git не попадает; шаблон — `.env.example`.

| Переменная | Дефолт | Описание |
|---|---|---|
| `HTTP_ADDR` | `:8080` | адрес HTTP-сервера |
| `DATABASE_URL` | `postgres://plata:dev@localhost:5433/plata` | подключение к PostgreSQL |
| `PROVIDER_URL` | `https://api.frankfurter.dev/v1` | внешний источник курсов |
| `WORKERS` | `2` | количество фоновых воркеров |
| `ALLOWED_CURRENCIES` | `USD,EUR,MXN` | поддерживаемые валюты (через запятую) |

Параметры воркеров (число попыток, пауза, интервал recovery, порог
зависания) заданы в `service.DefaultConfig()`.

## Разработка и тесты

```bash
make test     # go test ./...
make vet      # go vet ./...
make fmt      # gofmt -w .
make build    # статический бинарник в bin/
make docker-up / docker-down / docker-reset
```

Тестами покрыты пять пакетов: `model` (парсинг пары), `provider`
(успех/500/пустой ответ/битый JSON через httptest), `config` (дефолты
и переопределения), `service` (жизненный цикл задания, retry,
идемпотентный enqueue, recovery), `handler` (коды ответов 202/400/404/500,
JSON-контракт). Моки — ручные фейки, без внешних библиотек.

## Структура

```
cmd/server/          — точка входа: сборка зависимостей, graceful shutdown
internal/
  model/             — домен: CurrencyPair, RateUpdate, Rate, статусы
  config/            — конфигурация из окружения
  database/          — пул соединений с retry на старте
  repository/        — SQL: идемпотентный INSERT, claim через SKIP LOCKED, транзакция
  provider/          — клиент frankfurter (таймаут, проверка ответа)
  service/           — очередь, воркеры, retry, recovery
  handler/           — роутер, 3 эндпоинта, middleware (recover, логи)
```

Зависимости строго сверху вниз: `handler → service → repository/provider`.
Интерфейсы `RateRepository` и `RateProvider` объявлены в пакете-потребителе
(`service`), реализации подключаются в `main`.

## Технические решения

- **Идемпотентность гарантирует БД, а не процесс.** Partial unique index
  `(base, quote) WHERE status IN ('pending','in_progress')`: для пары
  не может быть двух незавершённых заданий, при любом числе инстансов.
  `ON CONFLICT ... DO UPDATE SET updated_at = rate_updates.updated_at` —
  намеренный no-op UPDATE: он заставляет `RETURNING` отдать существующую
  строку тем же запросом, без второго SELECT и без гонки между ними.
  Повторный POST возвращает id существующего задания, но не дублирует его
  в очередь: в очередь кладутся только реально созданные строки.
- **PostgreSQL — единственная очередь.** Воркеры забирают задания атомарным
  claim'ом: `SELECT ... FOR UPDATE SKIP LOCKED LIMIT N` с переводом в
  `in_progress` одним statement. Конкурентные воркеры — в том числе с разных
  инстансов — получают непересекающиеся партии: ни ожидания, ни дублей.
  Терминальные записи (`completed`/`failed`) условны —
  `AND status = 'in_progress'` — поэтому «медленный» воркер, опоздавший
  после сброса recovery, не перезапишет результат нового. UPSERT в `rates`
  обновляет строку только при более свежем времени — устаревшая котировка
  не затирает новую.
- **Сигнал — ускорение, поллинг — гарантия.** In-memory остался только
  сигнальный канал (буфер 1): POST будит воркеров мгновенно, сотня подряд
  идущих POST схлопывается в один сигнал. Потерянный сигнал не страшен:
  страховочный poll-тикер воркера и recovery-поллер каждые 30 секунд
  замечают работу в БД; recovery дополнительно сбрасывает зависшие
  `in_progress` (старше 5 минут — с запасом больше худшего цикла fetch ~16 с).
- **Результат фиксируется транзакцией.** Смена статуса на `completed` и
  UPSERT последней котировки — одна транзакция: обе записи или ни одной.
- **Graceful shutdown по порядку.** SIGTERM сливает HTTP-соединения
  (10 с), воркеры прерывают поход к провайдеру, но терминальную запись
  в БД делают на отдельном контексте (`context.WithoutCancel` + таймаут) —
  задание не зависает в `in_progress` из-за отмены.
- **`updated_at` — время получения котировки**, а не дата фиксинга ЕЦБ:
  клиент видит, когда сервис реально обновил значение. Дата данных
  провайдера в ответе не используется.
- **Цена: `NUMERIC(18,6)` в БД, `float64` в API.** Котировка предназначена
  для отображения и не участвует в денежных расчётах; если бы по курсу
  считались суммы — сквозной decimal.
- **Схема — init-скриптом Postgres** (`docker-entrypoint-initdb.d`):
  осознанное упрощение для тестового задания, работает при первом старте
  с чистым volume; изменение схемы — `docker compose down -v`. При
  эволюции схемы в живой базе нужен мигратор (goose/golang-migrate).

## Известные ограничения

- Сигнальный канал — per-instance: реплика, создавшая задание, будит только
  своих воркеров; остальные инстансы подхватывают работу по poll-тику
  (до 30 секунд). При жёстких требованиях к задержке — `LISTEN/NOTIFY`.
- Retry не различает временные и постоянные ошибки (4xx тоже ретраится) —
  допустимо при коротком цикле и малом числе воркеров, при росте нужна
  классификация ошибок и backoff.
- Frankfurter v1 помечен провайдером как deprecated, но продолжает
  отвечать; миграция на v2 — новая реализация `RateProvider`, остальной
  код не меняется.
- Идемпотентность действует только на незавершённые задания (coalescing),
  без `Idempotency-Key` и окна свежести.
